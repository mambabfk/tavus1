What is CVI?
CVI enables real-time, human-like video interactions through configurable lifelike replicas. Conversational Video Interface (CVI) is a framework for creating real-time multimodal video interactions with AI. It enables an AI agent to see, hear, and respond naturally, mirroring human conversation. CVI is the world's fastest interface of its kind. It allows you to map a human face and conversational ability onto your AI agent. With CVI, you can achieve low-latency utterance-to-utterance response: the full round-trip time from when a participant speaks to when the replica replies. CVI provides a comprehensive solution, with the option to plug in your existing components as required.
At a glance: CVI — Real-time multimodal video: the agent sees, hears, and responds; media runs over WebRTC (powered by Daily). Latency — Utterance-to-utterance round-trip is optimized for real-time use. Three pillars — Persona (behavior, knowledge, and CVI layer pipeline); Replica (visual digital human, Phoenix); Conversation (live session linking persona and replica). Pipeline (in order) — Perception (Raven) → Conversational Flow (Sparrow) → Speech recognition (STT) → Large language model (LLM) → Text-to-speech (TTS) → Realtime replica (Phoenix). Raven is visual perception; Sparrow handles turn-taking and interruptibility; Phoenix is the real-time visual replica engine. Where to configure — Most layers are set on the Persona.
Key Concepts: Persona defines the agent's behavior, tone, and knowledge, and configures the CVI layer and pipeline. Replica brings the persona to life visually, rendering a photorealistic human-like avatar using Phoenix. Conversation is a real-time video session that connects the persona and replica through a WebRTC connection.
Key Features: Natural Interaction (facial cues, body language, real-time turn-taking). Modular pipeline (customize Perception, STT, LLM and TTS layers). Lifelike AI replicas (100+ hyper-realistic stock replicas or your own). Multilingual support (42+ languages using supported TTS engines). World's lowest latency.
Pipeline layers: 1. Perception — Uses Raven to analyze user expressions, gaze, background, and screen content. 2. Conversational Flow — Controls turn-taking and interruptibility using Sparrow. 3. Speech Recognition (STT) — transcribes user speech in real time. 4. Large Language Model (LLM) — processes transcribed speech and visual input using a low-latency LLM. 5. Text-to-Speech (TTS) — converts the LLM response into speech using Cartesia (default) or ElevenLabs. 6. Realtime replica (Phoenix) — delivers a synchronized digital human using Tavus's real-time avatar engine.
Getting Started: create a conversation via the Developer Portal or the API Conversation Quickstart. For web apps, start with CVI App Quickstart, then choose an embed path in Embed CVI. React apps that want Tavus-provided UI should use the @tavus/cvi-ui component library (blocks, components, hooks, server helpers). Machine-readable references: https://docs.tavus.io/llms.txt (page index), https://docs.tavus.io/llms-full.txt (full bundled docs export), https://docs.tavus.io/openapi.yaml (HTTP API contract).

Conversation Overview
A Conversation is a real-time video session between a user and a Tavus Replica. It enables two-way, face-to-face interaction using a fully managed WebRTC connection.
Conversation Creation Flow: When you create a conversation, a WebRTC room (powered by Daily) is automatically created. You receive a meeting URL (e.g., https://tavus.daily.co/ca980e2e). The replica joins and waits in the room; timers for duration and timeouts begin. Billing: Credits begin counting when a conversation is created and the replica starts waiting in the room. Usage ends when the conversation finishes or times out. Each active session also uses one concurrency slot. You can use the provided URL to enter the video room immediately, or build a custom UI or stream handler instead of using the default interface.
What is Daily? Tavus integrates Daily as its WebRTC provider. You don't need to sign up for or manage a separate Daily account — Tavus handles setup and configuration. Use the default video interface or customize the Daily UI; embed the CVI in your app.
Identity and Context Setup: Persona — use a stock persona or create a custom one. If no replica is specified, the default replica linked to the persona is used. Replica — use a stock replica or create a custom one. If a replica is provided without a persona, the default Tavus persona is used. Conversation Context — customize the conversation context to set the scene, explain the user's role, say who joins the call, or point out key topics. Custom Greeting — personalize the opening line; the replica always finishes its greeting before it starts listening (participants can't interrupt it).
Advanced Customizations: Audio-Only Conversation (disable video for phone/low-bandwidth). Call Duration and Timeout (manage usage, costs, concurrency). Language (multilingual with real-time detection). Background Customization (green screen or custom background). Closed Captions (subtitles/live transcription). Call Recording (store in your own S3 bucket). Private Rooms (authenticated conversations with meeting tokens). Participant Limits (max participants).

Knowledge Base
Upload documents to your knowledge base for personas to reference during conversations. The Knowledge Base currently supports documents written in English and works best for English conversations. It uses RAG (Retrieval-Augmented Generation) to process and transform the contents of your documents and websites, allowing personas to dynamically access and leverage information during a conversation. During a conversation, the persona continuously analyzes conversation content and pulls relevant information from the documents selected during conversation creation as added context.
Getting Started: Upload documents or website URLs you intend to reference. Use the Developer Portal or API endpoints. Step 1: Ensure website resources are publicly accessible (no authorization required, e.g. a pre-signed S3 link). Step 2: Upload your documents via the Create Document API. Example POST to tavusapi.com/v2/documents: {"document_name": "test-doc-1", "document_url": "https://your.document.pdf", "callback_url": "webhook-url-to-get-progress-updates"}. The response includes a document_id. Supported formats: .pdf, .txt, .docx, .doc, .png, .jpg, .pptx, .csv, .xlsx. Step 3: Document processing happens in the background (5-10 minutes depending on size); status updates come via callback_url or the Get Document endpoint. Step 4: Create a conversation referencing the documents: {"persona_id": "your_persona_id", "replica_id": "your_replica_id", "document_ids": ["d1234567890", "d1234567891"]}.
Retrieval Strategy: specify document_retrieval_strategy to balance speed vs quality. speed — faster retrieval for minimal latency. balanced — balance of speed and quality. quality (default) — most relevant information, may take slightly longer. Example: {"persona_id": "...", "document_ids": ["d1234567890"], "document_retrieval_strategy": "balanced"}.
Document Tags: group documents with shared tag values instead of long lists of document_id. Set tags on Create Document: {"document_name": "test-doc-1", "document_url": "https://your.document.pdf", "tags": ["lesson-1"]}. On Create Conversation, pass document_tags instead of document_ids: {"persona_id": "...", "replica_id": "...", "document_tags": ["lesson-1"]}.
Website Crawling: Single Page Scraping (default) processes only the page you provide. Multi-Page Crawling: enable by providing a crawl config: {"document_name": "Company Docs", "document_url": "https://docs.example.com/", "crawl": {"depth": 2, "max_pages": 25}}. Crawl Parameters: depth (1-10) how many link levels to follow; max_pages (1-100) maximum pages to process. Crawl Limits: max 100 crawl documents per account, max 5 concurrent crawls, 1-hour cooldown between recrawls of the same document.
Keeping Content Fresh: trigger a recrawl with POST https://tavusapi.com/v2/documents/{document_id}/recrawl. Recrawl uses the same starting URL and crawl config, replaces old content, and updates last_crawled_at / crawl_count. You can override settings: {"crawl": {"depth": 3, "max_pages": 50}}. Requirements: document must be in ready or error state, at least 1 hour since last crawl, and must have been created with crawl configuration.
Best Practices for Documents: 1. Structure content by topic (one document per topic/feature/policy, clear section headers, avoid large master documents). 2. Keep documents focused and moderate in size (split long manuals). 3. Use high-quality, text-based sources (text-native PDFs, structured web content; avoid scans/images). 4. Be explicit and complete (definitions, constraints, exceptions, acronyms and full forms). 5. Avoid conflicting or duplicate sources (single source of truth). 6. Know when to use persona instructions instead (for content that must appear in every response, e.g. legal language). Quick Setup Checklist: one topic per document, no all-in-one manuals, text-based documents, clear headings/definitions, no duplicate/conflicting sources.

Guardrails
Guardrails provide your persona with strict behavioral guidelines followed throughout every conversation. They act as a safety layer alongside your system prompt to enforce rules, restrictions, and behavioral patterns. For example, a customer service persona for a financial institution can have guardrails that prevent discussing a competitor's products, sharing sensitive financial data, or providing investment advice outside approved guidelines. Each guardrail is its own resource — create, attach, edit, and delete guardrails independently via the Guardrails API. Guardrails are not guaranteed to prevent all misbehavior; they serve as guidance and should be part of a broader safety strategy.
Design tips: Be specific about restricted topics, behaviors, or responses. Consider edge cases where participants try to circumvent guardrails. Ensure guardrails complement rather than contradict the system prompt. Test with various scenarios. Think of guardrails as consistent reminders to the persona.
Writing guardrail prompts: Guardrails do two things — Steer the persona (it adheres to each guardrail), and Flag violations (continuously evaluated in the background; a violation triggers callback / app-message logic so you can react). They do not drive workflow progression — for goal-oriented steps, use Objectives. Good guardrail prompts are clear, specific, testable, and robust to user variation. Pattern: [who] [is doing what] [under what condition]. Examples: {"guardrail_name": "no_sensitive_data", "guardrail_prompt": "User is sharing full credit card numbers, social security numbers, or passwords"} and {"guardrail_name": "single_user_only", "guardrail_prompt": "More than one person is visible or speaking in the session"}.
